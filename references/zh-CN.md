# NH3 前端标准

NH3 是一个包含两个独立模式的多框架前端 Skill。它不再仅限 Vue，也不是把设计和工程规则混成一套的单一规范。

## 模式选择

调用者应选择一种模式：

- `frontend-engineering`：应用架构、实现、重构、操作型 UI、路由、状态、i18n、环境、安全、测试、构建和发布准备。
- `reference-site-design`：从参考中提取视觉、布局、动效和交互系统的公共营销、发布、活动和产品网站。
- `combined`：同时应用工程基线和参考驱动公共网站流程。仅在调用者明确要求两者时使用。

不得静默混用模式。若未指定模式，且目标表面无法明确判断，应要求调用者选择。后台仪表盘通常对应 `frontend-engineering`；强调视觉差异化的公共发布网站通常对应 `reference-site-design`。

## 共享基线

所有模式都遵循：

1. 编辑前检查目标仓库。Manifest、lockfile、源码、路由、测试、formatter、lint 配置、本地指令和既有约定是主要事实源。
2. 识别框架、渲染模式、包管理器、路由、状态方案、样式系统、测试工具和部署边界。不得仅从文件名推断架构。
3. 除非任务明确改变，否则保留既有能力和信息架构。视觉改版不授权改变路由、权限或工作流。
4. 保持改动聚焦。不得格式化无关文件、无必要替换既有依赖或回滚未知工作区改动。
5. 新增抽象、目录、组件、hooks、composables、services、stores 或规则文件前，先复用项目既有约定。
6. 尊重可访问性、reduced motion、错误处理、环境隔离、secret 边界和确定性包管理。
7. 报告改动文件、实际检查、未执行检查和已知限制。不得把编译或静态检查称为 UI 渲染验证。

## 保密与可移植边界

此 Skill 只包含框架无关标准。不得把私有项目源码、内部目录树、业务名称、路由、资源、配置值、基础设施细节或组织专属约定复制进 Skill，或放进对外复用的示例。

从真实项目抽象可复用指导时，只保留职责边界、判断标准和框架层关系；项目专属名称与结构必须改为中性示例。

## 框架与目录指导

既有仓库结构合理时遵循既有结构。新项目或结构修复应按职责和产品领域组织，不得把某个框架的目录树复制到其他框架。

选择或审查目录结构时读取 [framework-adapters.md](framework-adapters.md)。其中包含框架无关职责图，以及 React、Next、Vue、Nuxt、Svelte、SvelteKit、Angular、Solid、Astro 和类似技术栈的适配规则。

## 代码与换行标准

读取 [code-style.md](code-style.md)，了解换行符、缩进、折行、import 布局、多行语法、注释、生成代码例外和 formatter 优先级。

仓库 formatter 与 lint 配置优先。没有本地规则时，使用 UTF-8、LF 换行、文件末尾换行、无行尾空格；常见 Web 格式使用两个空格缩进，手写代码采用 100 列软限制。

## `frontend-engineering` 模式

实现或审查应用代码前，完整读取 [frontend-engineering.md](frontend-engineering.md)。

此模式优先保证：

- 路由与能力可达；
- 稳定的组件、状态、服务和领域边界；
- 紧凑、可扫描的操作型 UI；
- i18n 和真实用户状态；
- 环境、安全、性能和发布安全；
- 聚焦 diff 和与任务风险匹配的验证。

除非产品表面确实需要，否则不要在此模式应用公共网站 hero、活动型动效或编辑式构图规则。

## `reference-site-design` 模式

执行前完整读取：

1. [reference-design/mode.md](reference-design/mode.md)
2. [reference-design/system.md](reference-design/system.md)
3. 动效、滚动编排或实验性字体相关时读取 [reference-design/motion.md](reference-design/motion.md)
4. 交付前读取 [reference-design/review.md](reference-design/review.md)

此模式优先保证参考抽象、叙事场景、可替换媒体槽、项目级主题输入、有目的的动效、响应式重组和真实渲染证据。

不得因为工程模式存在紧凑后台规则，就把小型操作标题、紧凑密度或中性后台卡片模式套到公共营销网站。

## `combined` 模式

仅在明确选择时使用。先应用共享工程边界，再把参考驱动视觉系统应用到公共表面。按产品目的解决冲突：

- 工程模式负责数据、路由、状态、可访问性、安全、环境和可维护性；
- 参考设计模式负责公共页面构图、视觉层级、媒体处理、叙事动效和响应式体验；
- 既有仓库规则和用户明确指令覆盖两者。

## 验证策略

`frontend-engineering` 默认仅静态检查；只有调用者要求测试、构建、浏览器、运行时验证或发布检查时，才执行对应命令。验证时使用仓库既有命令。

实现 `reference-site-design` 时，桌面和紧凑屏真实渲染验证属于流程的一部分，除非调用者明确豁免；豁免时必须说明没有执行。

## 范围边界

NH3 适用于浏览器前端代码和全栈框架的前端表面。它可以分析 API 契约和服务端/客户端边界，但不治理纯后端服务、基础设施、原生 Android/iOS 应用或无关数据管道。

## 最终检查清单

声明完成前：

- 所选模式明确或不存在歧义；
- 框架建议匹配检测到的技术栈；
- 未将私有项目实现或命名复制进可复用指导；
- 路由、权限、操作和必需内容仍可达；
- 代码遵循仓库格式或 NH3 默认换行标准；
- 新抽象具有具体职责；
- 环境变量和浏览器暴露值不包含 secrets；
- 验证声明与实际执行一致。
